# 编码与文案协作约定

## 这份约定解决什么问题

项目里已经出现过多次中文乱码，直接带来了两个坏结果：

1. 页面文案显示异常，影响调试和交付。
2. 模型或开发者看不清原文语义，容易误判为“整段逻辑坏了”，从而重写过多代码。

这份文档就是为了把这个坑固定下来，后面不要再反复踩。

## 已确认的高风险原因

1. 不同编辑器或不同系统用不同编码保存同一个 `.dart` / `.md` 文件。
2. 文件本身是 UTF-8，但终端或编辑器按 GBK / ANSI 之类方式显示。
3. 在已经乱码的文件里继续追加中文，导致“新内容也被污染”。
4. 把大量中文文案直接散落在高频改动文件里，任何一次编辑都可能碰到编码问题。

## 后续统一规则

1. 所有源码、配置、文档一律使用 UTF-8。
2. 新建文件时优先确认编辑器默认编码是 UTF-8。
3. 如果某个文件已经明显乱码，不要在原地大面积续改。
4. 对乱码严重的文件，优先整段重建为干净 UTF-8 文件，再继续功能开发。
5. 提交前至少跑一次 `flutter analyze`，避免把乱码字符串、断裂字符串一起带进仓库。

## 实操建议

1. 看到终端乱码时，先不要立刻重写逻辑，先确认是“显示乱码”还是“文件内容真的坏了”。
2. 如果只是终端显示乱码，可以用编辑器直接打开文件确认真实内容。
3. 如果文件内容已经坏了，先备份，再做最小范围重建。
4. 修改中文密集文件时，尽量小步提交，避免一次性改太多看不清责任边界。
5. 高频中文文案后续可以逐步抽到集中配置或资源文件里，减少反复碰撞。

## 给 AI / 协作开发的额外规则

1. 发现文件里已有乱码时，优先小范围定位，不默认整页重写。
2. 先确认数据结构和调用链，再决定是否需要重建文件。
3. 对乱码重灾区，优先做“清编码”而不是“顺手大改功能”。
4. 任何因为乱码导致的重写，都要先说明是“编码问题”还是“真实逻辑问题”。

## 目前项目中的建议做法

1. `settings_screen.dart`、`capture_screen.dart`、`network_recommendation_screen.dart`、`backend/main.py` 这类中文较多且经常改动的文件，要特别注意编码。
2. 后续如果继续做 UI 文案整理，建议逐步把页面文本集中管理。
3. 新增文档时继续放在 `docs/` 下，统一 UTF-8 保存。
