# Android SDK Alignment Design

## Goal

Keep all current application features while reducing Android platform requirements
to SDK 34 and SDK 36 only.

The application and most Flutter plugins compile against SDK 36.
`flutter_secure_storage` remains on SDK 34. The following transitive Android
plugins currently hard-code SDK 35:

- `geocoding_android` 4.0.1
- `jni` 1.0.0
- `jni_flutter` 1.0.1

## Chosen Approach

Vendor the three SDK 35 plugins under `third_party/flutter_plugins/` and use
`dependency_overrides` to select those local copies.

The only source change inside each vendored plugin is:

```text
compileSdk 35 -> compileSdk 36
```

No Dart APIs, Java sources, native sources, package versions, `minSdk`, or
`targetSdk` values will change.

## Dependency Flow

The existing top-level dependencies remain unchanged:

- `geocoding` continues to provide geocoding features.
- `path_provider` continues to use `path_provider_android`.
- `path_provider_android` continues to use `jni` and `jni_flutter`.
- `flutter_secure_storage` continues to compile against SDK 34.

`pubspec.yaml` will add local overrides for only:

- `geocoding_android`
- `jni`
- `jni_flutter`

`pubspec.lock` will be regenerated by `flutter pub get`.

## Repository Layout

The vendored packages will live at:

```text
third_party/flutter_plugins/geocoding_android/
third_party/flutter_plugins/jni/
third_party/flutter_plugins/jni_flutter/
```

Each directory will preserve the complete upstream package needed by Pub and
Flutter tooling. Keeping the packages in the repository makes the patch
deterministic and prevents `flutter pub get` from overwriting it.

## Existing Worktree Changes

Existing uncommitted changes in Gradle configuration, `pubspec.lock`, and files
outside `today_eat_app` belong to the user and must be preserved. Implementation
will modify only the vendored packages, `pubspec.yaml`, and the lockfile entries
required by the local overrides.

## Verification

Verification will proceed in this order:

1. Add a repository-level check that resolves active Android plugin build files
   and fails if any selected plugin declares `compileSdk 35`.
2. Run the check before implementation and confirm that it fails on the current
   dependency set.
3. Add the local plugin overrides and update only the three `compileSdk` values.
4. Run `flutter pub get`.
5. Re-run the SDK declaration check and confirm that active modules use only 34
   or 36.
6. Run a clean Android debug build and confirm Gradle does not request Platform
   35.
7. Run the app on device `AHHSUT5915000779` and verify that it installs, starts,
   and remains attached.

The Android SDK ADB executable will be invoked from
`D:\ProgramData\Android\Sdk\platform-tools` before Flutter commands to avoid the
HonorSuite ADB server conflict.

## Platform 35 Cleanup

Platform 35 will not be removed until the clean build succeeds without using it.
After that verification, remove an incomplete or installed Platform 35 through
Android `sdkmanager`, not by deleting arbitrary SDK files.

Cleanup is limited to `platforms;android-35`. SDK 34 and SDK 36 remain installed.

## Failure Handling

- If a vendored plugin fails to compile with SDK 36, stop and report the exact
  plugin and compiler error instead of broadening the patch.
- If Pub selects a hosted package instead of a local override, fix path
  resolution before building.
- If Gradle still requests SDK 35, inspect the resolved plugin list for another
  hard-coded module before changing additional dependencies.
- If the phone disconnects, run the full-path SDK ADB device check before
  retrying Flutter.

## Non-Goals

- Removing geocoding, path provider, JNI, or secure storage features
- Changing application `minSdk` or `targetSdk`
- Editing the global Pub cache
- Applying a global Gradle override to every Android library
- Upgrading unrelated dependencies
