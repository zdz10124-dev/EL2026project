# 运动饮食健康一体化平台设计规格

## 1. 产品目标

将 `today_eat_app` 从饮食记录、推荐和总结工具，升级为运动、饮食、恢复一体化的个人健康平台。平台通过低成本记录、结构化指标计算和 AI 综合分析，形成“记录 -> 理解 -> 建议 -> 反馈”的健康闭环。

产品的核心创新不是简单并列饮食和运动功能，而是建立跨领域关联：运动负荷影响下一餐和恢复建议，近期饮食结构影响训练与休息建议，所有结论展示所依据的数据，并明确区分确定性指标、AI 推断和安全提醒。

## 2. 目标用户与核心场景

目标用户是希望改善饮食和运动习惯，但不愿使用多个专业应用或进行复杂录入的普通用户。

首期核心场景：

1. 用户拍摄餐食，AI 识别菜品与食材，用户确认后形成饮食记录。
2. 用户手动填写运动数据，或上传运动 App 截图，由 AI 提取结构化运动信息，用户确认后保存。
3. 平台汇总近 7 天或 30 天的饮食、运动和主观疲劳信息，生成饮食、运动或休息建议。
4. 用户在“今日”页面直接看到最重要的一至三条行动建议，并能查看建议依据。
5. 用户可继续使用原有“吃什么”、饮食日记、统计、社区推荐和导出能力。

## 3. 产品信息架构

底部主导航调整为四个一级入口：

1. `今日`：健康概览、今日行动建议、最近记录和快捷记录入口。
2. `记录`：饮食与运动双分类时间线，支持新增、编辑、删除和筛选。
3. `健康`：7/30 天综合分析、饮食分析、运动负荷、恢复状态和建议依据。
4. `我的`：AI 配置、健康目标、个人资料、主题、数据管理和社区设置。

原有“今天吃什么”不再独占一级导航，而作为“今日”页面的行动卡片和饮食工具入口。饮食日记、统计分析、偏好分析和联网推荐保留在健康页或饮食工具分区中。

## 4. 范围

### 4.1 首期必须交付

- 保留现有饮食记录、AI 识别、吃什么、日记、统计和社区推荐功能。
- 支持跑步、游泳、骑行、步行和其他五类运动。
- 支持手动新增运动记录。
- 支持从相册或相机导入运动截图并进行 AI 识别。
- AI 结果必须以可编辑草稿展示，用户确认后才能保存。
- 支持近 7 天和近 30 天综合健康分析。
- 生成饮食、运动和休息三类建议，允许某一类别为空。
- 每条建议展示依据记录或指标。
- 提供数据不足、AI 未配置、网络失败和解析失败的明确状态。
- 所有健康建议包含非医疗建议声明。

### 4.2 首期不做

- 不接入可穿戴设备或系统健康平台。
- 不自动估算疾病、诊断或处方。
- 不建设运动社区、排行榜或社交挑战。
- 不实现实时运动轨迹采集和 GPS 跑步记录。
- 不做复杂热量收支精算；缺少身体与份量数据时只输出趋势性结论。
- 不直接迁移或复用 CyberCoach 的 React 页面和 Hono 服务。

## 5. 领域模型

### 5.1 运动记录

新增独立的 `ExerciseRecord`，不向 `MealRecord` 塞入运动字段。

通用字段：

- `id`：本地数据库主键。
- `clientRecordId`：跨端稳定标识。
- `activityType`：`running | swimming | cycling | walking | other`。
- `startedAt`：运动开始时间。
- `durationSeconds`：运动时长。
- `distanceMeters`：可选距离。
- `averageHeartRateBpm`：可选平均心率。
- `peakHeartRateBpm`：可选峰值心率。
- `caloriesKcal`：可选消耗热量，标明用户输入或来源数据，不由模型伪造。
- `rpe`：可选主观疲劳评分，范围 1-10。
- `note`：用户备注。
- `imagePaths`：原始截图或照片。
- `source`：`manual | aiImage`。
- `createdAt`、`updatedAt`。

专项详情使用可空字段或序列化详情对象保存：

- 跑步：配速、步频、步幅。
- 游泳：泳姿、趟数、百米配速。
- 骑行：平均速度、爬升。
- 步行：步数、平均速度。

首期表单只要求运动类型、开始时间和时长。其他字段按类型显示并允许为空，避免识别不完整时无法保存。

### 5.2 健康档案

新增 `HealthProfile`：

- `goal`：`generalHealth | fatLoss | endurance | habit | performance`。
- `preferredActivities`：偏好运动类型集合。
- `availableDaysPerWeek`：可选。
- `maxSessionMinutes`：可选。
- `birthYear`、`heightCm`、`weightKg`：均为可选。

缺少可选身体数据时，系统禁止输出精确热量缺口、最大心率百分比或体重变化预测，只能使用记录中可验证的数据进行趋势分析。

### 5.3 综合健康分析

新增 `IntegratedHealthAnalysis`：

- `periodStart`、`periodEnd`、`generatedAt`。
- `dataFingerprint`：参与分析的数据指纹，用于缓存失效。
- `dataQuality`：记录数量、缺失字段和可信度说明。
- `overview`：总体摘要。
- `metrics`：本地确定性指标。
- `recommendations`：饮食、运动、休息建议集合。
- `riskAlerts`：仅包含保守提示，不进行医学诊断。
- `disclaimer`。

每条 `HealthRecommendation` 包含：

- `category`：`diet | exercise | rest`。
- `priority`：`low | medium | high`。
- `title`、`action`。
- `evidence`：引用的指标和记录摘要。
- `validUntil`：建议有效期。

## 6. 架构设计

保留当前本地优先策略，但拆出清晰的健康领域边界：

```text
AppDependencies
├── MealRepository
├── ExerciseRepository
├── HealthProfileRepository
├── HealthAnalysisRepository
├── HealthMetricsService
├── HealthAgentService
└── LlmService
```

### 6.1 数据仓库

- `MealRepository` 继续负责现有饮食领域，首期不全面改名。
- `ExerciseRepository` 负责运动图片、草稿、CRUD 和记录流。
- `HealthProfileRepository` 负责健康目标和可选身体资料。
- `HealthAnalysisRepository` 聚合饮食和运动记录，计算数据指纹，管理分析缓存并调用 `HealthAgentService`。

禁止页面直接操作 SQLite、SharedPreferences 或拼接 LLM Prompt。页面只消费仓库提供的状态和方法。

### 6.2 AI 服务

`LlmService` 只负责模型传输、超时、响应状态和 JSON 内容提取。结构化解析、字段校验和业务 Prompt 放在领域 Agent 中。

`HealthAgentService` 提供：

- `analyzeFoodImages`：保留现有能力。
- `analyzeExerciseImages`：从一至四张截图提取运动草稿。
- `analyzeNutrition`：保留饮食专项分析。
- `analyzeIntegratedHealth`：基于本地指标和记录摘要生成综合建议。

AI 输出必须经过三层处理：

1. 去除 Markdown 代码块并提取 JSON 对象。
2. 检查必需字段、枚举、范围和字段类型。
3. 对不合法输出返回可恢复错误，不静默伪装为真实 AI 结果。

正式交付默认使用 FastAPI 服务端代理，由服务端保存 API Key。客户端直连仅作为开发和离线部署选项，并在设置页明确提示密钥风险。

### 6.3 确定性指标与 AI 分工

`HealthMetricsService` 在本地计算：

- 饮食记录次数、餐次规律、食材和饮品出现频率。
- 运动次数、总时长、总距离、平均 RPE、高强度连续天数。
- 饮食与运动记录的时间关联，例如运动后 4 小时内是否存在饮食记录。
- 数据完整度和可分析性。

AI 只接收结构化摘要和必要的去标识记录，不负责重新计算总时长、距离或次数。这样可以减少幻觉，并让建议依据可展示和可测试。

## 7. 数据流

### 7.1 运动图片识别

```text
选择运动类型和图片
-> 本地预览
-> HealthAgentService.analyzeExerciseImages
-> 结构化校验
-> ExerciseDraft
-> 用户逐字段确认或修改
-> ExerciseRepository.save
-> SQLite 成功
-> 更新记录流
```

图片识别失败时保留图片和已填写草稿，允许用户转为手动录入。AI 不得直接保存记录。

### 7.2 综合健康分析

```text
选择 7/30 天范围
-> 拉取饮食和运动记录
-> HealthMetricsService 计算指标
-> 生成 dataFingerprint
-> 命中同指纹缓存则展示缓存
-> 未命中则调用 HealthAgentService
-> 校验建议和依据
-> 保存分析缓存
-> 展示综合结果
```

记录新增、修改或删除后，数据指纹变化，旧分析不会被当成当前结果。网络失败时可展示旧缓存，但必须标明生成时间和“数据已变化”。

## 8. 本地数据库与迁移

SQLite 数据库版本从当前版本递增，新增而不破坏现有表：

- `exercise_records`：运动记录。
- `health_analysis_cache`：综合分析缓存和数据指纹。

健康档案首期使用 SharedPreferences；若后续需要多用户同步，再迁移为数据库或服务端实体。

迁移要求：

- 原有 `meal_records` 和图片路径保持不变。
- 升级失败不得删除旧数据库。
- 新表创建必须幂等。
- 数据库迁移使用单独测试覆盖从当前版本升级和全新安装两条路径。

## 9. 服务端设计

扩展现有 `backend/main.py`，而不是同时维护 FastAPI 和 CyberCoach Hono 两套正式后端。

首期新增接口：

- `POST /v1/ai/exercise-recognition`：代理运动图片识别。
- `POST /v1/ai/health-analysis`：代理综合健康分析。

接口使用现有 JWT 鉴权。服务端不保存用户完整健康记录，只转发本次请求中的最小必要摘要；社区饮食上传继续沿用原接口。若后续需要跨设备同步，再独立设计同步协议。

服务端必须添加请求大小限制、图片数量限制、模型超时、结构化错误码和日志中的敏感信息脱敏。

## 10. UI 与交互设计

### 10.1 今日页

- 顶部显示当天日期和健康目标。
- 首屏展示一张“今日建议”主卡，只突出最高优先级行动。
- 次级卡展示饮食记录数、运动分钟数和恢复状态。
- 快捷操作为“记一餐”和“记运动”。
- “今天吃什么”作为饮食行动卡保留。

### 10.2 记录页

- 顶部使用“全部 / 饮食 / 运动”筛选。
- 时间线统一展示两类记录，但使用不同图标、色彩和摘要字段。
- 浮动新增按钮打开记录类型选择，再进入对应编辑器。
- 饮食编辑器复用现有拍照设计；运动编辑器遵循相同的“图片 -> AI 候选 -> 用户确认”模式。

### 10.3 健康页

- 显示 7 天和 30 天切换。
- 首屏显示总体概览、数据完整度和高优先级风险提示。
- 三个建议分区分别为饮食、运动和休息。
- 每条建议可展开查看依据。
- 专项入口保留营养分析、运动统计、偏好分析、日记和社区推荐。

## 11. 错误处理与降级

- AI 未配置：手动记录和确定性统计仍可用，综合分析展示配置入口。
- 图片识别失败：保留草稿并允许手动填写。
- JSON 解析失败：展示“模型返回格式异常”，不回退成伪 AI 固定结论。
- 网络超时：允许重试，已保存记录不受影响。
- 数据不足：明确列出缺少的记录或字段，不生成确定性过强的建议。
- 风险字段异常：例如峰值心率低于平均心率时阻止保存并提示修正。
- 所有健康分析显示“仅供生活方式参考，不作为医疗诊断或治疗建议”。

## 12. 测试策略

单元测试覆盖：

- `ExerciseRecord` 序列化和字段校验。
- SQLite 新建、升级、增删改查。
- 运动图片 AI 输出清洗和非法字段处理。
- 健康指标计算和数据指纹稳定性。
- 分析缓存命中、失效和陈旧缓存展示。
- 不同数据量下的降级策略。

Widget 测试覆盖：

- 手动运动录入与校验。
- 图片识别草稿的接受、拒绝和编辑。
- 记录筛选与双类型时间线。
- 今日页无数据、部分数据和完整数据状态。
- 健康页 AI 未配置、加载、成功、失败和陈旧缓存状态。

服务端测试覆盖：

- JWT 鉴权。
- 请求体和图片数量限制。
- 上游模型成功、超时、非 200 和非法 JSON。
- 日志不输出 API Key、JWT 和完整图片内容。

## 13. 实施阶段

### 阶段一：基础边界与可靠性

建立依赖装配、通用 AI JSON 解析、统一错误类型和测试基础；修复会阻碍重构的编码与同步问题，不改变现有用户路径。

### 阶段二：运动记录 MVP

交付运动模型、数据库、仓库、手动录入、图片识别草稿、记录列表和编辑删除。完成后即使没有综合分析，也是一套可独立演示的功能。

### 阶段三：综合健康分析

交付健康档案、确定性指标、缓存指纹、综合 AI Prompt、建议依据和健康页。

### 阶段四：主信息架构迁移

将底部导航迁移为“今日 / 记录 / 健康 / 我的”，重新安置原有饮食工具，并保持所有旧功能可达。

### 阶段五：服务端与比赛交付

增加领域化 AI 代理接口、安全限制和演示数据；完善关键测试、隐私说明、比赛展示流程和创新点文档。

## 14. 验收标准

- 用户可在不配置 AI 的情况下完成饮食和运动手动记录。
- 用户可上传运动截图，查看并编辑 AI 提取结果后保存。
- 饮食和运动记录在统一时间线中正确展示和筛选。
- 7/30 天分析使用当前记录，记录变化后不会误用旧缓存。
- 每条综合建议至少包含一条可展示依据，数据不足时明确说明。
- 本地保存不等待社区上传或其他非必要网络请求。
- 原有饮食记录、吃什么、日记、统计和社区推荐仍可访问。
- AI Key 默认不包含在发布客户端中。
- 自动化测试覆盖数据库迁移、核心指标、AI 解析和关键页面状态。
