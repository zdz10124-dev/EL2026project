# 食动智衡项目中期检查报告

> 提交日期：2026 年 7 月 25 日  
> 项目名称：食动智衡  
> 项目定位：运动、饮食与恢复一体化的个人健康 Agent

## 一、项目目标

食动智衡面向有饮食管理、运动记录和健康改善需求的普通用户，解决用户需要在多个应用间切换记录、难以理解饮食与运动关联、健康建议缺少依据的问题。

项目以“记录 - 理解 - 行动 - 反馈”为主线：用户通过餐食照片、手动输入或运动 App 截图低成本记录健康行为；系统在本地汇总饮食、运动、恢复与目标信息；AI 仅基于可验证的指标生成有依据的行动建议；用户可确认、完成或调整建议，形成持续优化闭环。

本项目不将 AI 简单作为聊天或报告生成工具，而是将其约束为个人健康 Agent 的决策与解释层。程序负责确定性指标计算和数据校验，AI 负责在明确边界内生成行动建议，从而降低模型幻觉与不可解释风险。

## 三、现阶段完成工作

### 1. 完成运动、饮食健康一体化基础能力

- 完成饮食记录功能，支持拍照或相册选择、多图展示、AI 菜品识别、人工确认、编辑和删除。
- 新增运动记录，支持跑步、游泳、骑行、步行及其他运动类型，可手动填写时长、距离、心率、主观疲劳评分等信息。
- 支持上传运动 App 截图，由 AI 提取截图中明确出现的运动数据，用户确认或修改后再保存。
- 将饮食与运动记录合并到统一时间线，支持分类筛选、详情查看、多图全屏浏览、编辑和删除。
- 完成“今日 / 记录 / 健康 / 我的”四级信息架构迁移，使运动与饮食不再作为彼此独立的附属功能。

### 2. 完成综合健康分析与可信 AI 基础

- 建立健康档案，支持设置健康目标、偏好运动、每周可运动天数、单次时长及可选身体数据。
- 实现近 7 天和近 30 天的确定性指标计算，包括饮食记录次数、运动次数、运动时长、距离、平均主观疲劳、连续高负荷日期和运动后饮食覆盖率。
- 实现综合健康分析，输出饮食、运动和休息三类建议，并展示每条建议引用的指标依据。
- 采用数据指纹和缓存机制，记录变化后旧分析不会被误认为当前结论；网络失败时可明确标识陈旧缓存。
- 完成服务端 AI 代理基础接口，支持运动截图结构化识别和综合健康分析，服务端模式可避免在正式客户端保存模型密钥。

### 3. 完成健康 Agent 前三项基础任务

为从“健康分析工具”升级为“健康 Agent”，项目已完成以下底层能力：

- 完成每日恢复打卡数据模型与 SQLite 迁移。用户后续可记录睡眠质量、疲劳、肌肉酸痛和精力，评分范围为 1 至 5。
- 完成健康上下文计算服务，将当天饮食、当天运动、近 7 天指标、恢复状态、健康目标与行动反馈汇总为去标识化上下文，并生成稳定数据指纹。
- 完成 Agent 行动模型和严格解析器。行动被限定为饮食、运动、休息三类，最多三条；每条行动必须引用本地白名单证据，未知跳转目标、无依据内容和医疗诊断/治疗措辞会被拒绝。
- 已为恢复仓库、健康上下文、数据指纹和行动解析器新增定向自动化测试，验证评分范围、同日更新、数据不足、指纹失效、证据校验和医疗措辞拦截等关键逻辑。

### 4. 完成比赛交付基础材料

- 编写创新点说明，明确多模态低成本记录、跨域关联分析、确定性计算与生成式 AI 分工、建议依据可追溯等创新点。
- 编写演示脚本和隐私与 AI 边界说明。
- 提供脱敏演示数据，便于在真机上快速展示饮食、运动与综合分析流程。
- 完成应用品牌升级，名称调整为“食动智衡”，版本更新为 2.0.0。

## 四、阶段性成果与创新点

项目当前的核心成果不是简单将饮食页面和运动页面并列，而是建立了跨领域的健康数据关联能力：运动负荷会影响饮食与恢复建议，饮食记录可用于判断运动后是否及时进餐，恢复打卡将成为判断当日行动强度的重要输入。

与普通运动记录 App 相比，项目强调饮食、运动、恢复三类信息的协同；与大众点评式饮食推荐产品相比，地点、价格、评分和联网推荐不再是核心路径，产品的主价值转向个人健康状态理解与下一步行动安排。

与普通健康问答相比，项目先以本地程序计算可复核指标，再让 AI 在证据白名单约束下解释和排序建议。该机制使建议具备可追溯性，并减少由大模型直接计算健康数据导致的不稳定结论。

## 五、现存问题

### 1. Agent 闭环尚未完成页面与服务端接入

恢复打卡、健康上下文和行动解析已经完成，但每日行动计划尚未接入 LLM 调用、缓存编排和今日页主行动卡。用户暂时还不能在应用中完成“生成行动 - 执行 - 完成/跳过 - 重新规划”的完整流程。

### 2. 恢复状态尚未形成正式交互入口

恢复打卡数据层已具备，但恢复打卡页面、每日提醒和今日页入口尚未实现。当前综合健康分析中的休息建议仍主要基于运动与饮食记录，缺少用户当天主观状态的直接输入。

### 3. 历史功能的产品权重仍需调整

原项目保留了联网推荐、地点、价格、评分、点赞和评论等功能。虽然这些能力可以作为饮食工具保留，但若在比赛演示中占据过多篇幅，仍可能使项目被理解为大众点评类应用，需要在后续 UI 与演示路径中继续降低其曝光。

### 4. 自动化测试覆盖仍不充分

当前已覆盖新增底层逻辑的关键用例，但数据库真实升级、每日计划缓存状态、服务端每日计划接口和今日页交互仍需补充测试。由于 Flutter/Dart 在 Codex 沙盒用户下无法稳定访问 SDK，验证需要使用本机用户权限执行定向命令，后续应继续控制验证频率并保留真机测试记录。

### 5. 数据来源仍以用户手动输入为主

项目尚未接入穿戴设备、Health Connect 或 Apple Health。手动记录和截图识别适合首期演示，但长期使用时需要进一步降低输入成本，同时保证隐私授权和数据最小化。

## 六、后续规划

### 第一阶段：完成每日 Agent 行动闭环

- 接入每日 Agent 计划生成、缓存和失效机制。
- 在今日页突出一个最高优先级行动，并展示产生依据。
- 增加完成、跳过和“太难”反馈，使系统能够在数据变化后重新规划。
- 在 AI 未配置或网络失败时提供本地降级行动，不阻塞记录功能。

### 第二阶段：完善场景化饮食与教练能力

- 将“今天吃什么”从随机和历史偏好推荐升级为健康场景决策，例如训练后补充、恢复日饮食或记录不足提醒。
- 增加近 7 天行动历史、完成率和反馈统计。
- 融合已有 CyberCoach 项目中的训练计划、单次运动恢复反馈和下一次训练建议，形成周级计划能力。

### 第三阶段：优化比赛展示和稳定性

- 将比赛主流程固定为“恢复打卡 - 记录饮食/运动 - Agent 主行动 - 查看依据 - 反馈调整”。
- 将联网推荐、美食日记和消费统计放入次级饮食工具，避免干扰健康 Agent 主定位。
- 补充服务端结构化校验、隐私脱敏、缓存失效、失败降级和真机回归测试。
- 在功能稳定后评估系统通知和可穿戴设备数据接入，不在当前阶段引入额外复杂依赖。
